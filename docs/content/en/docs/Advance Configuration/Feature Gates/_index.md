Redis Operator supports feature gates to enable alpha/experimental features. These can be configured in the Helm chart values.

## Configuration

Feature gates can be configured in the Helm chart values:

```yaml
featureGates:
  # Enable generating Redis configuration using an init container instead of a regular container
  GenerateConfigInInitContainer: false
  # Never execute redis-cli -a <password>, even if authentication cannot succeed without it
  AvoidCommandLinePassword: false
  # Keep the pod template of existing StatefulSets when only the operator version changed it
  DeferPodTemplateUpdates: false
```

## Available Feature Gates

### AvoidCommandLinePassword

When enabled, Redis Operator will never execute `redis-cli -a <password>`, which can leak passwords. The Operator sets the
`REDISCLI_AUTH` variable on all Redis pods, so the password does not need to be provided on the command line and it is normally
safe to turn this on unless you are simultaneously upgrading the operator. This is an alpha feature and may change in future releases.

However, if you upgrade from a version that does not add `REDISCLI_AUTH` to the pods (a behavior introduced in the same version that
added `AvoidCommandLinePassword`), simultaneously enabling `AvoidCommandLinePassword` will make Redis Operator unable to manage
your current pods, since `-a <password>` is still needed on them. Hence, to guarantee that the Redis password will never be included
on a command line, you must either risk an operator downtime or upgrade in two steps:

1. Upgrade to a version that adds `REDISCLI_AUTH` to the pods (which was introduced at the same time as `AvoidCommandLinePassword`).
2. Turn on `AvoidCommandLinePassword`.

**Default**: `false`

**Usage**:
```yaml
featureGates:
  AvoidCommandLinePassword: true
```

### DeferPodTemplateUpdates

Every operator release can change the pod template it generates for a Redis StatefulSet: a new init container image,
new labels, environment variables, probes or preStop hooks. Without this gate, upgrading the operator therefore re-creates
every Redis pod it manages, at a time the owners of those Redis instances did not choose.

When enabled, the operator does not change the pod template of an existing StatefulSet when only the operator changed it.
The pods keep running with their current template, and the template generated by the running operator is applied, with the
usual rolling update, the next time the owner changes the custom resource:

- any change of the spec (`metadata.generation`), labels or annotations of the `Redis`, `RedisReplication`, `RedisSentinel`
  or `RedisCluster` resource;
- or, to apply it without any other change, a new value of the `redis.opstreelabs.in/apply-pod-template` annotation on the
  resource. This annotation is not copied to the StatefulSet or the pods.

```shell
kubectl annotate redisreplication my-redis --overwrite redis.opstreelabs.in/apply-pod-template="$(date +%s)"
```

Fields of the StatefulSet outside the pod template, such as the number of replicas, are still updated as usual. A spec
change applies the whole template the running operator generates, including the changes it brought, for every
StatefulSet of that resource (both the leader and the follower StatefulSet of a `RedisCluster`).

The operator keeps the state on each StatefulSet in these annotations:

| Annotation | Meaning |
|---|---|
| `redis.opstreelabs.in/pod-template-update-pending` | `true` when the running operator would generate a different pod template than the StatefulSet carries. |
| `redis.opstreelabs.in/pod-template-inputs` | Key of the resource inputs the current template belongs to. |
| `redis.opstreelabs.in/pod-template-hash` | Hash of the template the operator last wrote. |

To list the StatefulSets with a pending template:

```shell
kubectl get statefulsets -A -o json | jq -r '.items[]
  | select(.metadata.annotations["redis.opstreelabs.in/pod-template-update-pending"] == "true")
  | "\(.metadata.namespace)/\(.metadata.name)"'
```

Enabling the gate together with an operator upgrade is supported: StatefulSets that do not have the annotations yet are
adopted with their current template. A change of the resource that is applied by the same reconcile that adopts the
StatefulSet is held back as well and shows as pending.

While a template is pending, any change of the resource rolls the pods, including a change that would not have touched
the pod template on its own, such as scaling.

When the gate is disabled again, the operator stops maintaining these annotations; the values left on the StatefulSets
are stale and the generated template is applied on the next reconcile.

The StatefulSet of the Sentinel embedded in a `RedisReplication` (`spec.sentinel`) is covered as well, but for one written
before the gate was enabled the operator cannot tell whether a template change is pending until the resource changes once.

**Compatibility rule.** With this gate, the operator manages pods that run the pod template of the previous operator
version. Apply the pending templates (for example by changing the resource or setting the annotation above) before the
next operator upgrade; pod templates older than the previous minor version are not supported. In particular:

- The container image the previous template refers to, including the `INIT_CONTAINER_IMAGE` init container image, must
  stay pullable until the template is applied, because a pod that is re-created for another reason (node drain, eviction)
  uses the template it has.
- Behaviour that lives in the pod template, such as a new preStop hook, only takes effect once the template is applied.
- Do not enable `AvoidCommandLinePassword` while pods still run a template without the `REDISCLI_AUTH` variable (older
  than v0.27): the operator refuses to authenticate to them on the command line.
- Changes the operator renders from objects other than the resource itself, such as the operator's own environment, are
  deferred too. Changes of a related `RedisSentinel` that affect a `RedisReplication` template and NodePorts allocated
  for a `RedisCluster` count as resource changes.

This is an alpha feature and may change in future releases.

**Default**: `false`

**Usage**:
```yaml
featureGates:
  DeferPodTemplateUpdates: true
```

### GenerateConfigInInitContainer

When enabled, Redis configuration will be generated using an init container instead of a regular container. This is an alpha feature and may change in future releases.

**Default**: `false`

**Usage**:
```yaml
featureGates:
  GenerateConfigInInitContainer: true
```

## Feature Gate Lifecycle

Feature gates follow a standard lifecycle:

1. **Alpha**: Features are disabled by default and may be changed in incompatible ways in a later software release without notice.
2. **Beta**: Features are enabled by default and may be changed in incompatible ways in a later software release.
3. **GA**: Features are enabled by default and will not be changed in incompatible ways in a later software release.

{{< alert color="warning" title="Warning" >}}
Alpha features are experimental and may be changed or removed in future releases. Use them with caution in production environments.
{{< /alert >}}

## Adding New Feature Gates

When adding new feature gates to Redis Operator:

1. Define the feature gate in `internal/features/features.go`
2. Add the feature gate to `DefaultRedisOperatorFeatureGates`
3. Update the Helm chart values to include the new feature gate
4. Update this documentation with the new feature gate details
